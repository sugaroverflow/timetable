# 2026-10-03 — Web Push step 1: subscription tables and kind defaults (#368)

Step 1 of `docs/web-push-plan.md` §6, built to Ed's 2026-10-03 rulings
(§5). Data and pure logic only: nothing calls it yet, so it ships inert.
Step 2 (API config, VAPID, encryption, transport) is being built in
parallel on its own branch; the routes, GraphQL fields and mutation wiring
that call these functions come once both have landed.

## What was built

**Migration 0045 (`0045_web_push.sql`)**, additive only (R11): two new
tables, nothing existing altered.

- `push_subscriptions`: one row per device. `user_id` (FK to `user`,
  cascade), `endpoint` (unique), `p256dh`, `auth`, optional `label`,
  `created_at`, `updated_at`, `last_sent_at`, `failure_count` (default 0),
  plus a `user_id` index. Keyed to the user, not the membership as #360
  had it, because a subscription is a device and covers every forum on it.
- `push_sweep_state`: the step 3 sweep's cursor. One row, enforced by a
  `CHECK (id = 1)`; the migration seeds it (`swept_until = now()`, a
  hand-added `INSERT … ON CONFLICT DO NOTHING` after the generated DDL), so
  the compare-and-set in §3.2 always has a row to compare against.

The per-forum Push switches need no column: they are the new optional
`push` field of `MembershipDigestSettings`, inside the existing
`digest_settings` jsonb. `updateMembershipDigestSettings` already does a
shallow jsonb merge, so a `{ push: … }` patch leaves the email switches
alone and vice versa.

**Shared (`packages/shared/src/push.ts`)**:

- `PUSH_KIND_DEFAULTS` (every `DIGEST_KINDS` row): on for `comments`,
  `replies`, `mentions`, `lounge`, `sessions`, `sessionsHostHearted`,
  `availabilityAsks`; off for the broadcast kinds; `drafts` false.
- `PUSH_EVENTLESS_KINDS = ["drafts"]`, `isPushEventlessKind`, `PushKind`.
- `isPushKindEnabled(kinds, kind)`: the membership's switch, else the
  default; eventless kinds always false. No forum-defaults layer (email
  has one): alerts are opt-in per device, so a forum can't switch a phone
  on.
- `pushUrgency(kind | null)`: `high` for on-by-default kinds and the
  switch-less sent-back notice, `normal` otherwise (the transport's
  `Urgency` header).
- Alert text: `pushTitle` ("who in where", " · forum" when asked, capped
  at 120), `pushBodyLine` (first non-empty line, Markdown stripped on
  request, trimmed at a word boundary to about 100 characters with "…"),
  `trimAtWord` (code-point safe, so an emoji is never split),
  `markdownToPlainText`, `isSafePushUrl` (same-origin path only: no `//`,
  no backslash, no control characters), `serializePushPayload` (the JSON
  the service worker reads, kept under 3 KB, null for an unsafe url).
- Device input: `PUSH_DEVICE_CAP = 10`, `PUSH_ENDPOINT_MAX`,
  `PUSH_LABEL_MAX`, `normalizePushKeys` (base64url shape of the 65-byte
  P-256 point and the 16-byte auth secret, padding stripped),
  `normalizePushLabel`.

**Core (`packages/core/src/push.ts`)**: #360's `managePush` split into
four calls, so each route is a one-liner:

- `subscribePush(userId, { endpoint, p256dh, auth, label? })` →
  `{ ok: true, created, device }` or `{ ok: false, reason: "invalid" |
  "taken" | "cap" }`. Under `pg_advisory_xact_lock` on the endpoint, then
  on the user (always that order, so no deadlock). Same user + endpoint
  refreshes keys/label and resets `failure_count`, keeping `created_at`.
  An endpoint owned by another account is `taken`: never moved silently.
- `unsubscribePush(userId, endpoint)` → whether the caller's row went.
- `listPushDevices(userId, currentEndpoint?)` → devices without endpoints
  or keys, `current` marking the asking browser.
- `hasPushSubscription(userId, endpoint)`.
- `isPlausiblePushEndpoint` (https URL, sane length; the push-service host
  allowlist stays in step 2's `validPushEndpoint`) and
  `PUSH_LOCK_NAMESPACE` (`sweep` / `endpoint` / `user`, the first int of
  the two-int advisory-lock form; step 3 takes `sweep`).

Database errors are re-thrown as a fixed "Push subscription operation
failed", because Drizzle's messages embed the query parameters, and the
endpoint is a capability.

## Not built here (on purpose)

- The sweep's claim of `push_sweep_state` (advisory lock, 10 s lag,
  10-minute cap, compare-and-set) and result recording (`last_sent_at`,
  `failure_count`, deletion on gone): the plan puts those in step 3, with
  the sender that uses them.
- Routes, GraphQL, the `pushSubscribe` action limit, the endpoint host
  allowlist: step 2 and the wiring PR.

## Checked

- `packages/shared/src/push.test.ts` (32 tests): the default map against
  plan §1, eventless `drafts`, push switches independent of email ones,
  key shapes, trimming (word boundary, single long word, emoji), Markdown
  stripping, title, url safety, payload size budget.
- `apps/api/src/push-core.test.ts` (12 tests): core through
  `@timetable/core` with `@timetable/db`'s `db` faked (the repo has no
  DB-backed core tests, and none were invented): invalid input never
  reaches the database, create takes both locks, refresh keeps the label
  and resets failures, `taken`, the cap at 10 and at 9, sanitised errors,
  unsubscribe, device list without endpoints.
- Against a real Postgres 16 (fresh database, `npm run db:migrate`, then a
  throwaway script, not committed): the seeded sweep row, create/refresh,
  `taken` for a second user, the cap's 11th device refused, and **a race**
  of four concurrent subscribes from a user at 9 devices: exactly one
  succeeded, three got `cap`, which is what the user lock is for.
